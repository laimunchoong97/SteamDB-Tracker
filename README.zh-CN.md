# SteamDB 即将发售游戏追踪器

[English](README.md) | [简体中文](README.zh-CN.md)

这是一个基于 Node.js 的 Windows 工具，用于从 SteamDB 采集即将发售的 Steam 游戏，保留关注人数历史，为达标游戏补充 Steam 商店元数据，并生成格式化的 Excel 工作簿。工作簿支持英文、简体中文，或一次性生成两种语言。

## 工具功能

1. 根据**本地抓取日期**，计算与**当前自然月**和**下一个自然月**相交的所有 ISO 周。
2. 依次打开这些周对应的 SteamDB 即将发售页面。
3. 按关注人数从高到低排序。
4. 将所有成功抓取的游戏写入 `steamdb_master_data.json`。
5. 仅对达到关注人数阈值的游戏请求 Steam 商店元数据。
6. 仅使用达标游戏生成本地化 Excel 工作簿。
7. 按**游戏的发售月份**（而不是抓取月份）分组到不同工作表。
8. 根据最新关注人数计算动态的 `当前评级`（P0 至 P3）。

这样既能保持 Excel 分析聚焦，又不会丢弃关注人数较低的原始数据。

## 自然月抓取

抓取窗口不再使用固定的六周，而是根据日历计算：

- 工具读取**本地抓取日期**。
- 选择**当前自然月**和**下一个自然月**。
- 收集与这两个月份任意一天相交的所有 **ISO 周**。
- 由于 ISO 周会跨越月份边界，因此可能包含溢出到上一个月或下一个月的周。工具会抓取这些周的全部 SteamDB 页面并保存所有行。
- 只有当每一个预期周的表格都成功加载时，抓取才算**完整**。只要有一个预期周失败，本次抓取就**不会提交**，原有历史保持不变。

示例：2026 年 9 月 30 日抓取，覆盖 2026 年 9 月和 10 月。9 月对应第 36–40 周，10 月对应第 40–44 周，因此预期集合为 `2026W36` 至 `2026W44`（共 9 周）。

## 发售月份可见性规则

工具根据**最近一次完整抓取日期**决定各发售月份是「活跃」「冻结」还是「隐藏」。

- **活跃月份**：最近完整抓取所在的发售月份，以及紧随其后的一个发售月份。只有这两个月份是活跃的。即使某个月没有达标游戏，也会生成对应工作表。
- **隐藏的未来月份**：晚于下一个活跃月份的发售月份。其游戏仍保留在 `steamdb_master_data.json` 中，当该月成为活跃月份时会自动显示。
- **归档月份**：早于当前活跃月份的发售月份。其工作表会被永久冻结在 `steamdb_release_archives.json` 中，并始终由该不可变快照重新生成，而不是读取最新主数据。未进入归档的历史月份不会显示。
- **未定档期**：没有明确发售月份的达标游戏，按最近一次完整抓取刷新。

归档只代表**当前活跃月份开始之前**已经存在的观测。当抓取日期进入新的月份时，历史月份会基于抓取前的状态被冻结，并将关注人数历史裁剪到当前月份开始之前，因此新月份的溢出数据绝不会填充或篡改已完成的月份。仅在溢出中首次出现的游戏不会被加入上个月的归档。

行为示例：

- 以当前本地主数据（最近完整抓取为 `2026-09-30`）执行重建时，会显示活跃的 **2026年9月** 和 **2026年10月**（若没有 9 月游戏，则 9 月为空表），并隐藏 **2026年11月**。
- 将来在 2026 年 10 月完成一次抓取后，**2026年9月** 会冻结在其最新的 9 月观测值，**2026年10月** 和 **2026年11月** 变为活跃。9 月发售游戏的 10 月溢出数据会写入主数据，但不会改动已冻结的 9 月工作表。
- 如果第一次抓取就发生在 10 月，且只看到 9 月发售游戏的溢出、没有任何 10 月之前的观测，则不会创建也不会显示 9 月工作表或 9 月归档。
- 某个月份一旦进入归档，后续抓取或阈值变化都不会再修改它。缺失的历史月份会在下一次完整抓取或重建确认其应存在时自动补齐。

「汇总」工作表和「达标即将发售」工作表**只**包含来自**最近一次完整抓取**、且属于两个活跃发售月份的达标游戏，因此不再出现在最新抓取中的旧游戏不会残留其中。活跃月份工作表仍可保留其已存储的达标游戏。

## 输出语言

在 `.env` 中设置工作簿语言：

```env
OUTPUT_LANGUAGE=both
```

| 取值 | 输出文件 |
|---|---|
| `en` | `steamdb_upcoming_tracker.xlsx` |
| `zh-CN` | `steamdb_upcoming_tracker_zh-CN.xlsx` |
| `both`（默认） | 同时生成以上两个文件 |

选择 `both` 时，两个工作簿由**同一份内存数据**一次性生成，不会重复抓取，也不会重复调用 Steam API。

只有工作簿中的固定文案会被翻译：工作表名称、列标题、状态、汇总的标题/卡片/表格、当前评级标签、固定的「是/否」、发行商/开发商/游戏类型/功能标签/支持平台缺失时使用的固定 `N/A` 标记，以及链接提示。抓取得到的真实值（游戏名称、发行商、开发商、游戏类型、功能标签等）永不翻译。中文使用 **微软雅黑（Microsoft YaHei）** 和兼容 Excel 的 `yyyy-mm-dd` 日期格式，英文使用 **Aptos / Aptos Display**。

如果在测试或脚本中显式传入 `excelFile`，除非同时指定 `language`，否则只生成一份英文工作簿。

## 可见性规则

最新关注人数决定游戏是否出现在 Excel 中：

- `最新关注人数 >= FOCUSED_THRESHOLD` 时可见。
- 低于阈值的游戏会从所有工作表和汇总统计中隐藏。
- 工作簿不显示被隐藏游戏的数量。
- 所有游戏仍保留在 JSON 主数据中。
- 当游戏跨过阈值时，会带着完整的历史关注人数自动出现。
- 当最新关注人数跌破阈值时，会再次隐藏，但不会丢失历史。

默认阈值为 1,000 关注人数，可在 `.env` 中修改，但当前评级框架强制最低为 1,000。

## 发售月份规则

Excel 月份工作表代表游戏计划发售的时间：

- 9 月发售的游戏会出现在 `2026年9月`，即使它是在 8 月或 9 月抓取的。
- 只有月份、没有具体日期的游戏（如 `Oct 2026`）会出现在 `2026年10月`，单元格保持文本。
- 精确日期在写入 Excel 前会统一为 UTC 零点，防止在 GMT+8 等时区出现日期前移一天。
- 如果 SteamDB 将发售从 9 月改到 10 月，下一次完整抓取时该行会移动到 `2026年10月`，而冻结的归档工作表保持不变。
- Coming Soon、仅年份、仅季度等没有具体月份的日期会进入「未定档期」。
- 已发售的游戏仍保留在其发售月份工作表中，因为历史游戏保存在主数据中。

## Excel 工作簿

生成的工作簿结构如下：

```text
汇总 | 达标即将发售 | <归档月份> | <活跃月份> | 未定档期
```

归档月份工作表按时间顺序排列在活跃月份之前。两个活跃月份工作表始终存在，即使为空。历史月份只来自冻结归档；未归档的历史月份和未来月份都不会渲染为工作表。

### 汇总

仪表盘包含：

- 最近完整抓取
- 达标即将发售
- 本次新增
- 30天内发售
- 当前发售月份
- 下一发售月份
- 未定档期
- 关注人数阈值
- 发售月份概览
- 较上次抓取增长榜
- 30天内即将发售（前25）

汇总中的游戏指标和表格只使用达到当前阈值的活跃月份游戏。`距发售天数` 有意从明细工作表中移除，只出现在汇总的 30 天发售规划表中。

### 达标即将发售

包含属于两个活跃发售月份、且在最近完整抓取中出现的达标游戏。归档月份和未来月份不会出现在这里。

### 发售月份工作表

活跃月份工作表始终存在（即使为空），包含该月所有已存储的达标游戏，可能多于最近一次抓取返回的游戏。归档月份工作表是由 `steamdb_release_archives.json` 渲染出的冻结快照，只基于当前活跃月份之前的观测构建，在后续抓取和阈值变化中保持稳定。未归档的历史月份不会显示。

### 未定档期

包含无法归入具体月份的达标游戏，按最近一次完整抓取刷新。

## 列说明

核心字段始终排在最前，随后是 API 与计算字段，最后是为每个抓取日期生成的一列关注人数。

| 列（en / zh-CN） | 来源 | 说明 |
|---|---|---|
| 发售日期 | SteamDB | 精确 Excel 日期，或仅月份/未定档期文本 |
| 游戏名称 | SteamDB | 游戏名称，链接到 SteamDB 页面 |
| 关注人数 | SteamDB | 最新抓取到的关注人数 |
| 发行商 | Steam 商店 API | 达标游戏的发行商列表 |
| 开发商 | Steam 商店 API | 达标游戏的开发商列表 |
| 当前评级 | 计算 | 基于最新关注人数的 P0–P3 评级 |
| 是否免费 | Steam 商店 API | 游戏是否免费 |
| 游戏类型 | Steam 商店 API | Steam 类型列表 |
| 功能标签 | Steam 商店 API | 单人、合作、手柄支持等功能 |
| 支持平台 | Steam 商店 API | Windows、macOS、Linux |
| AppID | SteamDB | 链接到 Steam 商店页面的 AppID |
| 状态 | 计算 | 即将发售、今日发售、已发售、已发售（按月份）、本月发售、即将发售（按月份）、未定档期 |
| 上次抓取关注人数 | 计算 | 该游戏上一次可用的关注人数 |
| 较上次抓取变化 | 计算 | 最新关注人数减去上一次，并非 7 天指标 |
| 首次发现 | 计算 | 首次抓取到该游戏的日期 |
| 最近更新 | 计算 | 包含该游戏的最近一次完整抓取 |
| `YYYY-MM-DD` 列 | 历史 | 每个抓取日期记录到的关注人数 |

## 当前评级框架

工具使用四个互斥的关注人数区间，给出一个简洁评级，不生成愿望单、销量或收入估算。

| 等级 | 关注人数区间 | 当前评级（英文） | 当前评级（中文） |
|---|---:|---|---|
| P0 | 30,000+ | AAA | AAA |
| P1 | 10,000–29,999 | AA | AA |
| P2 | 3,000–9,999 | Indie | 独立游戏 |
| P3 | 1,000–2,999 | Barely Viable | 勉强可行 |

显示值会合并等级与名称，例如 `P1 - AA`。当前评级在每次生成工作簿时重新计算，随着临近发售关注人数增长可能提升。它只是一个排序辅助，并不代表商业结果保证。

## 安装

### 面向非技术同事的 Windows 安装包

不使用 Git 或命令行的同事可以直接使用以下任一安装包：

- `SteamDB-Tracker-Setup.exe` — 推荐使用，提供开始菜单和可选桌面快捷方式
- `SteamDB-Tracker-Windows-x64.zip` — 便携版，使用前请完整解压整个文件夹

安装或解压后，打开 **SteamDB Tracker.exe**。双语图形界面提供：

- 英文、简体中文或双语工作簿选择
- 关注人数门槛设置
- **运行抓取**按钮
- **重建 Excel**按钮
- 打开英文/中文工作簿或输出文件夹的按钮
- 运行进度和错误日志

安装包已包含 Node.js 运行时和 npm 依赖。最终用户无需安装 Node.js、npm、Git、Playwright Chromium 或 Inno Setup。Cloudflare 验证仍然需要 Microsoft Edge。

安装程序默认使用 `%LOCALAPPDATA%\Programs\SteamDB Tracker` 下的当前用户目录，不需要管理员权限。追踪历史和设置保存在该安装中。

生成的可执行文件尚未进行代码签名，因此 Windows SmartScreen 可能显示“未知发布者”。如需在公司内大规模分发，建议使用公司可信的代码签名证书对安装程序进行签名。

### 构建 Windows 安装包

维护者可在 Windows 上执行：

```powershell
npm run package:windows
```

该命令会编译图形启动器、打包 Node.js 与 `node_modules`、验证便携运行环境、生成 `dist/SteamDB-Tracker-Windows-x64.zip`，并在安装 Inno Setup 6 后生成 `dist/SteamDB-Tracker-Setup.exe`。SHA-256 校验值会写入 `dist/SHA256SUMS.txt`。`dist/` 下的生成文件不会提交到 Git。

## 运行抓取

推荐流程：

1. 如果 `steamdb_upcoming_tracker.xlsx` 或 `steamdb_upcoming_tracker_zh-CN.xlsx` 处于打开状态，请先关闭。
2. 双击 `start_tracker.bat`。
3. Microsoft Edge 会以远程调试模式打开。
4. 如果出现 Cloudflare 验证，请手动完成。
5. 等待 SteamDB 表格加载完成。
6. 回到命令行窗口，按任意键。
7. 工具会抓取两个自然月的周、补充达标游戏、保存 JSON 历史、更新归档，并重新生成工作簿。

如需手动连接到已在调试端口 `9222` 运行的 Edge：

```bash
npm run remote
```

## 配置

### 关注人数阈值

在 `.env` 中设置：

```env
FOCUSED_THRESHOLD=1000
```

该设置同时控制：

- 哪些游戏在 Excel 中可见
- 哪些游戏会请求 Steam 商店 API 元数据

比较是包含的，因此关注人数恰好为 1,000 的游戏也算达标。P3 框架强制最低为 1,000：调高会进一步缩小工作簿，而更低、缺失、非法、为零或负数都会解析为 1,000。

修改阈值后，关闭 Excel 并执行以下命令，即可无需重新抓取地刷新活跃工作表：

```bash
npm run rebuild
```

阈值变化不会影响已冻结的归档工作表。

```env
OUTPUT_LANGUAGE=both
```

可选值为 `en`、`zh-CN`、`both`。详见 [输出语言](#输出语言)。

抓取窗口由日历自动推导，无需手动配置。工具始终以当前自然月和下一个自然月为目标，并在运行时计算相交的 ISO 周。

## 数据与更新行为

### 完整抓取

只有当每个预期周的 SteamDB 表格都成功加载时，抓取才会提交。工具会先基于抓取前状态冻结历史月份，再把本次抓取合并进主 JSON，最后重新生成 Excel 工作簿。

### 不完整抓取

如果任一预期周加载失败：

- 本次抓取不会写入主数据历史。
- 原有历史关注人数不会被覆盖。
- 工作簿仅基于最近一次完整存储的数据重新生成。
- 最近完整抓取日期不会推进。
- 会生成 `debug_cloudflare_YYYYWNN.png` 截图以便排查。

### 发售归档

`steamdb_release_archives.json` 保存过去达标发售月份的不可变、带版本号的快照。每个归档条目保留该工作表精确重现所需的完整游戏数据、关注人数历史、计算状态和评级。快照基于抓取前状态采集，并将历史裁剪到当前活跃月份开始之前，因此更新的溢出观测绝不会污染归档。归档条目永不被重写。

### Steam 元数据缓存

Steam 元数据保存在主 JSON 中，后续运行会复用。默认使用 3 个并发工作线程，并对请求启动时间做全局间隔控制；遇到 Steam API 限流或临时错误时会自动退避。启动器会显示逐个游戏的进度、完成百分比和预计剩余时间。每个请求默认在 15 秒后超时（可通过 `STEAM_API_TIMEOUT_MS` 调整）；并发数和请求间隔可通过 `STEAM_API_CONCURRENCY` 与 `STEAM_API_REQUEST_SPACING_MS` 调整。失败或不可用的记录会在之后重试。

### 日期与时区处理

抓取历史键使用本机日历日期。日期写入 Excel 前会被构造为 UTC 零点，因此 ExcelJS 在序列化时不会将其前移一天。例如在 GMT+8 运行时，底层为 `2026-10-01` 的发售仍会在 10 月工作表和可见的发售日期单元格中显示为 `01 Oct 2026`。

如果从早期版本升级后仍出现日期前移一天，请关闭所有 Excel 副本并运行 `npm run rebuild`，从不变的 JSON 历史重新生成所有可见日期。

## 故障排查

### Excel 文件被占用

启动器会在抓取或重建前检查所选输出工作簿是否被 Excel 占用。如果出现提示，请关闭 `steamdb_upcoming_tracker.xlsx` 和 `steamdb_upcoming_tracker_zh-CN.xlsx` 后重试。如果抓取已完成，但工作簿在预检后被打开并导致生成失败，请关闭 Excel，然后点击 **重建 Excel**；完整抓取数据已经保存，无需再次抓取。

### Excel 提示中文工作簿内容有问题

旧版中文工作簿使用了部分 Excel 版本会尝试修复的本地化日期格式，问题位于 `styles.xml`。当前版本已改用兼容性更好的 `yyyy-mm-dd`。关闭工作簿后运行 `npm run rebuild`，即可替换旧文件。

### Cloudflare 或某一周失败

运行 `start_tracker.bat`，完成浏览器验证，等待表格出现，然后在命令行窗口按键。工具会有意拒绝不完整抓取，以保护历史数据。

### 发行商或开发商为空

该游戏可能低于阈值、Steam 商店 API 暂不可用，或正在等待失败请求的重试。

### Excel 中缺少某个游戏

请在 `steamdb_master_data.json` 中检查其最新关注人数。只有最新值达到 `FOCUSED_THRESHOLD` 时才会出现；即使被隐藏，其历史也会保留。

### 缺少某个未来月份

晚于下一个活跃月份的月份会被有意隐藏。当日历推进、其成为活跃月份后会自动恢复显示。

### 日期仍然前移一天

关闭工作簿的所有打开副本并运行 `npm run rebuild`。在能够成功重新生成之前，现有工作簿不会被修改。

### 只生成了一个工作簿

检查 `.env` 中的 `OUTPUT_LANGUAGE`。使用 `both` 可同时生成英文和简体中文文件。

## 共享仓库

其他人可以克隆仓库，运行 `npm install`，将 `.env.example` 复制为 `.env`，然后按批处理文件流程操作。生成的历史、归档和 Excel 文件均为本地文件，因此每位用户都从独立的数据开始。
